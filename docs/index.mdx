A [Better Auth](https://better-auth.com/) plugin for signing in with Nostr. The server verifies a [NIP-98](https://github.com/nostr-protocol/nips/blob/master/98.md) signed HTTP event and issues an ordinary Better Auth session; no password or private key ever reaches it. Each user can link several Nostr keys.

This page takes you from nothing to a first Nostr sign-in. The [guide](guide.md) covers signers (NIP-07, nsec, NIP-46), profiles and relays and how sign-in works, the [reference](reference.md) every endpoint, client action and error code, and [support and versioning](support.md) what is tested and what a version number promises.

This site follows `main`. For the docs of the version you have installed, open `https://github.com/leon-wbr/better-auth-nostr/tree/vX.Y.Z/docs`; releases from before this site existed have only their README.

## Installation

<Steps>

1. ### Install the plugin

   <Tabs syncKey="pkg">
   <TabItem label="npm">
   ```bash
   npm install better-auth better-auth-nostr
   ```
   </TabItem>
   <TabItem label="pnpm">
   ```bash
   pnpm add better-auth better-auth-nostr @better-auth/core @better-auth/utils @better-fetch/fetch nanostores
   ```
   </TabItem>
   <TabItem label="yarn">
   ```bash
   yarn add better-auth better-auth-nostr @better-auth/core @better-auth/utils @better-fetch/fetch nanostores
   ```
   </TabItem>
   <TabItem label="bun">
   ```bash
   bun add better-auth better-auth-nostr @better-auth/core @better-auth/utils @better-fetch/fetch nanostores
   ```
   </TabItem>
   </Tabs>

   npm 7 and later installs the other peer dependencies (`@better-auth/core`, `@better-auth/utils`, `@better-fetch/fetch`, `nanostores`) for you. With another package manager, add them yourself.

2. ### Add the plugin to your auth config

   ```ts title="auth.ts"
   import { betterAuth } from "better-auth";
   import { nostr } from "better-auth-nostr";

   export const auth = betterAuth({
     baseURL: "https://app.example.com",
     plugins: [nostr()],
   });
   ```

   :::caution
   Set `baseURL`, or `BETTER_AUTH_URL`. The signed event is bound to the endpoint URL, and without a configured base URL Better Auth derives it from the request's `Host` header, which an attacker controls, so in production the plugin refuses to start without one. [Why baseURL matters](guide.md#why-baseurl-matters) explains it.
   :::

3. ### Migrate the database

   The plugin adds one model, `nostrPubkey` (see [Schema](#schema)). Create it with Better Auth's CLI:

   <Tabs>
   <TabItem label="migrate">
   ```bash
   # Kysely adapter: applies the change
   npx auth@latest migrate
   ```
   </TabItem>
   <TabItem label="generate">
   ```bash
   # Prisma or Drizzle: writes the schema for your own migration
   npx auth@latest generate
   ```
   </TabItem>
   </Tabs>

   Each linked key is also registered as an `account` row with `providerId: "nostr"`, so Better Auth's own account APIs see it. Keys linked by an older version get theirs on the user's next sign-in; see [the guide](guide.md#managing-linked-keys) before upgrading to 1.0.

4. ### Add the client plugin

   ```ts title="auth-client.ts"
   import { createAuthClient } from "better-auth/client";
   import { nostrClient } from "better-auth-nostr/client";

   export const authClient = createAuthClient({
     baseURL: "https://app.example.com",
     plugins: [nostrClient()],
   });
   ```

   The client signs against `baseURL + basePath`, which has to match the URL the server checks. If Better Auth is mounted somewhere other than `/api/auth`, pass the same `basePath` here.

</Steps>

## Usage

### Sign in with an extension

With a NIP-07 extension such as Alby or nos2x installed, this is all a sign-in button needs:

```ts
const { data, error } = await authClient.signIn.nostr();
if (error) console.error(error.code, error.message);
```

The first sign-in with a new key creates a user, named after the npub and with Better Auth's placeholder email `npub1…@nostr.placeholder.invalid`. Set [`disableSignUp`](#options) to allow only keys that are already linked, [`allowSignUp`](guide.md#deciding-who-can-sign-up) to decide per key, or [`generateEmail`](#options) to choose the email. The action never throws: a failure comes back as `error`, with a stable [`error.code`](reference.md#error-codes).

No extension? Pass `{ nsec }` or a NIP-46 remote signer instead; the [guide](guide.md#signers) shows each.

### Link a second key

A signed-in user can link another key, for example a backup:

```ts
await authClient.nostr.addPubkey({ nsec: backupNsec, name: "Backup key" });
```

Either key then signs in to the same account. Linking a key that already belongs to someone else fails with `NOSTR_PUBKEY_LINKED_TO_OTHER_USER`.

### List, rename and remove keys

<Tabs syncKey="side">
<TabItem label="Client">
```ts
const { data: pubkeys } = await authClient.nostr.listPubkeys();
await authClient.nostr.updatePubkey({ id, name: "Laptop" });
await authClient.nostr.removePubkey({ id });
```
</TabItem>
<TabItem label="Server">
```ts
const pubkeys = await auth.api.listPubkeys({ headers });
await auth.api.updatePubkey({ body: { id, name: "Laptop" }, headers });
await auth.api.removePubkey({ body: { id }, headers });
```
</TabItem>
</Tabs>

Each entry is `{ id, publicKey, npub, name, createdAt, lastUsedAt }`. Removing needs a fresh session and is refused for the user's last way to sign in: see [Managing linked keys](guide.md#managing-linked-keys).

## Schema

The plugin adds one model, `nostrPubkey`. Each row links one Nostr key, `publicKey` in hex, to one user; a user can have several. Better Auth adds the `id` primary key, `name` is the label from `addPubkey({ name })`, and `lastUsedAt` the time of the key's latest sign-in. Generated from the plugin's `schema`:

{/* generated:schema */}

| Field | Type | Required | Unique | Indexed | References |
| --- | --- | --- | --- | --- | --- |
| `name` | string |  |  |  |  |
| `publicKey` | string | yes | yes | yes |  |
| `userId` | string | yes |  | yes | `user.id`, on delete cascade |
| `createdAt` | date | yes |  |  |  |
| `lastUsedAt` | date |  |  |  |  |

{/* /generated:schema */}

Rename the model or its columns with Better Auth's `schema` option, as for its own plugins: `nostr({ schema: { nostrPubkey: { modelName: "nostr_keys", fields: { publicKey: "pub_key" } } } })`. Each key also has a row in Better Auth's own `account` table, with `providerId` `"nostr"` and the hex key as `accountId`; keys linked before that get theirs [on the user's next sign-in](guide.md#managing-linked-keys), until 1.0. Nonces are kept in Better Auth's `verification` table, under identifiers starting with `nostr:`, and are deleted when used.

## Options

### Server

`nostr(options?)` takes these, all optional. Generated from `NostrOptions`; the [API page](api/better-auth-nostr/client.md#nostroptions) has the full types.

{/* generated:server-options */}

| Property | Default value | Description |
| ------ | ------ | ------ |
| `relays?` | `none` | Relays this app reads from, at least one. This library never picks relays for you. On the server, a new user is filled from their kind `0` profile at sign-up (best effort; sign-up waits on the lookup up to `relayTimeoutMs`); when unset, the server never contacts a relay. On the client, `nostr.getProfile` reads from them; without them it is missing from the client's types and returns `NOSTR_RELAYS_NOT_CONFIGURED`. |
| `relayTimeoutMs?` | `5000` | How long to wait on relays, in milliseconds. |
| `disableSignUp?` | `false` | Reject sign-ins from keys that are not linked to a user yet (`NOSTR_PUBKEY_NOT_REGISTERED`) instead of creating a user. |
| ~~`disableImplicitSignUp?`~~ | `undefined` | **Deprecated** Use `disableSignUp`; removed in 1.0. |
| `allowSignUp?` | `every new pubkey may sign up` | Decides, sync or async, whether a pubkey with no user yet may sign up. Runs on sign-in only, after the NIP-98 event and nonce have been verified; never for linked keys or `nostr.addPubkey`, and not at all when `disableSignUp` is set. `false` rejects with `NOSTR_SIGN_UP_DISABLED` (403) and creates nothing; a throw propagates. |
| `schema?` | `undefined` | Rename the pubkey model and its columns, for an existing table, as with Better Auth's own plugins. **Example** ``{ nostrPubkey: { modelName: "nostr_keys", fields: { publicKey: "pub_key" } } }`` |

| `schema.nostrPubkey.fields.userId?` | `...` | - |
| `schema.nostrPubkey.fields.createdAt?` | `...` | - |
| `schema.nostrPubkey.fields.lastUsedAt?` | `...` | - |
| ~~`modelName?`~~ | `undefined` | **Deprecated** Use `schema.nostrPubkey.modelName`; removed in 1.0. |

| `generateEmail?` | `npub1…@nostr.placeholder.invalid` | The email of a user created at sign-in, sync or async. Receives the npub and the hex pubkey. |
