This page describes what better-auth-nostr defends against, how, and what it deliberately leaves to Better Auth, to your app and to the user's signer. It is the scope document for the external audit tracked in [#76](https://github.com/leon-wbr/better-auth-nostr/issues/76). To report a problem, see the [security policy](https://github.com/leon-wbr/better-auth-nostr/blob/main/SECURITY.md).

Code references point at [`2fc33ca`](https://github.com/leon-wbr/better-auth-nostr/tree/2fc33caf81ad30febb39a0097158d205cd6c71cf), the 0.8.0 code, so the line numbers stay valid as `main` moves on. The checks done by dependencies were read in nostr-tools 2.25.2 and Better Auth 1.7.12, the versions in the lockfile.

## Assets

- **Sessions.** A sign-in ends in a Better Auth session and its cookie. Whoever holds the cookie is the user until the session expires or is revoked.
- **Pubkey-to-user links.** A `nostrPubkey` row, mirrored by a `nostr` row in Better Auth's `account` table, says which user a key signs in as. Every linked key has the same rights, so whoever can add a row for their own key to someone else's user owns that user.
- **Nonces.** Each one is a single-use permission for one pubkey to sign in or link once, within its TTL.
- **The user's secret key** never reaches the server. On the client it lives in a NIP-07 extension, a NIP-46 remote signer, or, with the `nsec` option, in page memory.
- **The NIP-46 client key.** Apps persist it, with the `bunker://` URI, to resume a remote-signer session without a new approval.
- **User profile fields** (`name`, `image`, additional fields) that the plugin may fill from a kind `0` profile.

## Trust boundaries

| Party | Trusted for | Not trusted for |
| --- | --- | --- |
| Server running the plugin, its config and database | Everything; it is the party being protected | |
| Better Auth | Sessions, cookies, CSRF and origin checks, the verification table, rate limiting, account linking rules | |
| nostr-tools | Schnorr signature checks, NIP-98 event validation, relay pool, NIP-46 transport | |
| Browser and the app's own scripts | Running the client plugin as shipped | |
| Signer (NIP-07 extension, NIP-46 remote signer, a custom `NostrSigner`) | Holding the key and signing what the user approves | Returning an event from the key it claims, with a valid signature, signed just now |
| Relays | Availability, best effort | The content of anything they serve, and withholding nothing |
| NIP-05 hosts, `nprofile` relay hints | Nothing on the server, which never contacts them | Anything, in the browser |
| Request headers and bodies | Nothing | Everything; `Host` in particular, unless `allowDynamicBaseURL` is set |

## Sign-in with NIP-98

A sign-in is two requests. The flow for linking a key (`/nostr/add-pubkey`) is the same, plus a session.

1. **Nonce.** The client asks the extension or signer for its pubkey and posts it to `/nostr/nonce` ([client.ts:177-185](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/client.ts#L177-L185)). The server checks it is 64 hex characters ([routes.ts:355-359](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L355-L359)), draws 16 random bytes from `crypto.getRandomValues` ([routes.ts:37-40](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L37-L40)), or calls the app's `getNonce`, whose output must match `[A-Za-z0-9_-]{8,249}` ([routes.ts:384-389](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L384-L389)). It stores one verification row per nonce, keyed `nostr:<nonce>`, holding the lowercased pubkey and expiring after `nonceTtlMs`, five minutes by default ([routes.ts:391-395](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L391-L395), [routes.ts:34](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L34)). Because each nonce has its own row, a second nonce request for the same key doesn't invalidate the first ([routes.ts:46-51](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L46-L51)).
2. **Token.** The client builds a kind `27235` event with nostr-tools' `getToken`, tagged with the endpoint's absolute URL, the method `post` and the SHA-256 of `{ nonce }`, and has the signer sign it ([client.ts:147-171](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/client.ts#L147-L171)). The URL is `baseURL + basePath + path`, built by the same function on both sides so the tag matches byte for byte ([endpoints.ts:16-25](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/endpoints.ts#L16-L25), [client.ts:87-102](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/client.ts#L87-L102)). The token goes in the `Authorization` header and the nonce in the body ([client.ts:213-218](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/client.ts#L213-L218)).
3. **Verification.** `verifyNip98Request` ([routes.ts:77-107](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L77-L107)) requires the header and a non-blank nonce, unpacks the event, and calls nostr-tools' `validateEvent` with the server's own URL for this endpoint, `post`, and `{ nonce }` rebuilt from the body. That checks, in order: the Schnorr signature over the event id, kind `27235`, `created_at` within 60 seconds of the server clock either way, the `u` tag equal to the URL, the `method` tag, and the `payload` tag equal to the hash of `{ nonce }`. Only after all of that passes does it consume the nonce ([routes.ts:57-69](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L57-L69)): Better Auth's `consumeVerificationValue` reads and deletes the row, and the stored pubkey must equal the event's signer.
4. **Session.** The signer's pubkey row is looked up; a new key creates a user and its pubkey row in one transaction ([routes.ts:298-348](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L298-L348)), unless `disableImplicitSignUp` is set ([routes.ts:428-436](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L428-L436)). Better Auth then creates the session and sets its cookie ([routes.ts:462-479](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L462-L479)).

## Threats and mitigations

Each row names the mitigation and the test that covers it. Test links point at the same commit.

### Who may sign up

Implicit sign-up is on by default: any key that passes the checks above gets a new user ([routes.ts:428-436](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L428-L436)). Generating keys costs nothing, so an open install can be filled with users at the rate the sign-in limit allows. `disableImplicitSignUp` rejects every key that isn't linked yet with `401 NOSTR_PUBKEY_NOT_REGISTERED`, tested at [integration.test.ts:196](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/tests/integration.test.ts#L196). Better Auth's `databaseHooks.user.create.before` can veto a user too, but sees only the user object.

`allowSignUp` ([#73](https://github.com/leon-wbr/better-auth-nostr/issues/73), not released yet) adds a per-key decision between the two. Its design keeps these properties, which its tests have to cover:

- It runs only after the NIP-98 event and the nonce have been checked and the nonce consumed, so it only sees a pubkey that proved it holds the key, and an unsigned request can't probe an allowlist.
- It runs only for a key with no pubkey row: neither existing users nor `addPubkey` are gated.
- `false` writes nothing and answers `403 NOSTR_SIGN_UP_DISABLED`; a throwing callback is a 500, never an implicit yes.
- `disableImplicitSignUp` is checked first, so the callback never runs when it is set.
- The `profile` it receives is the self-claimed kind `0` event, or `null` without `relays` or when no relay answers. A relay can withhold it, and its `nip05` is unverified, so a gate must not grant access on profile content alone.

### Sessions

The plugin creates sessions only through Better Auth's `internalAdapter.createSession` and `setSessionCookie` ([routes.ts:463-478](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L463-L478)), and its session-guarded endpoints use Better Auth's `sessionMiddleware` and `freshSessionMiddleware`. Cookie attributes, session lifetime and refresh, revocation, `freshAge`, and the origin and CSRF checks on cookie-authenticated requests are Better Auth's and configured there. A session before-hook that refuses to create a session gets a vague `401`, not a 500 ([routes.ts:468-475](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L468-L475), tested at [integration.test.ts:295](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/tests/integration.test.ts#L295)).

A sign-in request carries its proof in the `Authorization` header, which a cross-site form can't set, and the nonce it needs is bound to a key the attacker would have to hold.

### Relays and profile data

With `relays` configured, the server fills a new user's `name` and `image` from their kind `0` profile ([routes.ts:226-269](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L226-L269)). Without `relays` it never opens a connection ([routes.ts:235](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L235)).

| Slow or failing relays blocking sign-up | The lookup runs before the transaction, waits at most `relayTimeoutMs` (5 s by default), and any failure means no profile fields ([routes.ts:306-307](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L306-L307), [routes.ts:262-268](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L262-L268)). | [autofill.test.ts:127](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/tests/autofill.test.ts#L127), [autofill.test.ts:206](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/tests/autofill.test.ts#L206) |

Profile text is self-claimed. A `name` is not verified, not unique and not length-limited by the plugin: render it as untrusted text, and don't treat it, or the `nip05` field, as proof of anything.

In the browser, `nostr.getProfile` does follow `nprofile` hints and resolve NIP-05 identifiers ([client.ts:277-284](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/client.ts#L277-L284)), so looking up an input the user didn't choose connects their browser to hosts the input names, which learn their IP address.

### Abuse and rate limits

The nonce, sign-in and link endpoints have default limits of 10 per 60 s, 3 per 10 s and 5 per 60 s, overridable per endpoint ([index.ts:21-25](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/index.ts#L21-L25), [index.ts:114-120](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/index.ts#L114-L120), tested at [safeguards.test.ts:40-62](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/tests/safeguards.test.ts#L40-L62)). They are enforced by Better Auth's rate limiter, so they apply only where `rateLimit.enabled` is on, by default in production ([types.ts:97-106](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/types.ts#L97-L106)), and they key on the client address Better Auth sees, so behind a proxy its IP header settings matter.

## Known gaps

These are open, listed here so the audit and users see them. None lets someone sign in as a key they don't hold.

- **Linking a key needs a session, not a fresh one.** `/nostr/add-pubkey` uses `sessionMiddleware` ([routes.ts:488](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L488)), while removing uses `freshSessionMiddleware` ([routes.ts:643](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L643)). Someone who steals a session cookie can link a key of their own, which still signs in after the stolen session is revoked. Until this changes, revoking sessions after a theft must go with checking `nostr.listPubkeys`, as [Key loss and recovery](key-loss.md#lost-versus-stolen) says.
- **A mismatched signer burns the nonce.** The nonce row is deleted before its pubkey is compared ([routes.ts:62-68](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L62-L68)), so anyone who learns a pending nonce can void it with a token from any key. Nonces travel only between the client and the server, so this needs an attacker who can already read that traffic, and costs the user one retry.
- **The key's `name` is not signed.** The payload hash covers `{ nonce }` only ([client.ts:191](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/client.ts#L191), [routes.ts:96](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L96)), not the `name` sent next to it to `/nostr/add-pubkey`. Changing it in flight takes the same position as above and only changes a label.
- **Nonce requests are unauthenticated and each writes a row.** Anyone can ask for nonces for any pubkey ([routes.ts:381-397](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L381-L397)). Rows expire with `nonceTtlMs`; how soon expired rows are deleted is up to Better Auth and the database. With rate limiting off, this grows the verification table.
- **The account backfill runs on every new session.** Until 1.0 removes it ([#69](https://github.com/leon-wbr/better-auth-nostr/issues/69)), a database hook adds missing `account` rows for a user's keys whenever a session is created ([index.ts:43-55](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/index.ts#L43-L55), [routes.ts:185-211](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/src/routes.ts#L185-L211)). It only adds rows for keys already linked to that user.

## Untested mitigations

These mitigations hold in the code but no test would fail if they broke:

- **A bad signature on a NIP-98 token.** The tests change the URL, method, payload and time of a validly signed token, but none sends one whose signature doesn't verify, so dropping nostr-tools' `verifyEvent` from the path would go unnoticed.
- **Forged or mismatched profile events from a relay.** `fetchProfile`'s tests mock the pool, so the signature and `authors` checks nostr-tools' pool makes are never exercised.
- **Cross-site sign-in requests.** Nothing tests that a sign-in without the `Authorization` header, or from an untrusted origin, fails in a browser-shaped request; the `400 NOSTR_MISSING_TOKEN` test ([nip98-verification.test.ts:90](https://github.com/leon-wbr/better-auth-nostr/blob/2fc33caf81ad30febb39a0097158d205cd6c71cf/tests/nip98-verification.test.ts#L90)) covers only the header.

## Out of scope

- **Better Auth itself:** cookies, session storage and lifetime, CSRF and origin checks, the verification table, the rate limiter, other sign-in methods and plugins. Report those to Better Auth.
- **nostr-tools' cryptography and NIP implementations.** The plugin relies on its signature checks, NIP-98 validation, relay pool and NIP-46 transport.
- **The user's key custody:** a key stolen from the user's device, extension or remote signer signs in as them. What the app can do about that is in [Key loss and recovery](key-loss.md).
- **Signer apps and extensions:** their storage, their approval prompts, and what they sign beyond the permissions requested.
- **The app around the plugin:** XSS, how it renders profile data, where it stores an `nsec` or a NIP-46 client key, its `getNonce`, `generateEmail` and `mapProfileToUser`, its TLS, proxy and database configuration.
- **Relay availability and censorship.** A relay that withholds a profile only means no profile fields.
- **NIP-05 verification on the server**, which the plugin doesn't do. Adding it ([#74](https://github.com/leon-wbr/better-auth-nostr/issues/74)) would bring outbound requests to user-chosen hosts into scope.
- **Denial of service** beyond the rate limits above.
